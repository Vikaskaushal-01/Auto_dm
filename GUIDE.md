# Going Live: Connecting Real Meta Platforms (Instagram, Facebook, WhatsApp)

This app currently runs entirely in **demo mode** — every account, conversation, and metric is generated by seeded Postgres data and served through `DemoInstagramConnector`, `DemoFacebookConnector`, and `DemoWhatsAppConnector`. The architecture was built so that switching any single platform to real data is a matter of finishing the matching `GraphAPI*Connector` class and flipping `PlatformConnection.mode` from `DEMO` to `LIVE` — nothing else in the app needs to change, because every page/action already goes through the connector interfaces, never the demo classes directly.

This guide walks through everything required to make that switch real, platform by platform, plus the shared plumbing (OAuth, webhooks, token storage) all three platforms need.

---

## 0. What "real" requires, before touching code

All three platforms — Instagram, Facebook Pages/Messenger, and WhatsApp Business — are configured through **one Meta Developer App**. You do not create three separate apps.

You will need:

1. A **Meta Developer account** at [developers.facebook.com](https://developers.facebook.com) (a personal Facebook account tied to a real identity — Meta requires this for App Review).
2. A **Meta Business Account** (business.facebook.com) — required to add WhatsApp and to complete Business Verification.
3. A **publicly reachable HTTPS domain** for OAuth redirect URIs and webhook callbacks. `localhost` only works for local testing with Meta's tunneling tools (ngrok) — production webhooks require a real TLS certificate.
4. **Business Verification** (government business documents, submitted to Meta) — required before WhatsApp will let you send messages beyond a small test tier, and before Meta grants several App Review permissions.
5. Patience for **App Review** — any permission beyond what your own test accounts can use (`instagram_basic` on your own IG account, etc.) requires Meta to review a screencast of your app using that permission before it goes live for other users.

None of this can be done purely in code — it's an approval process on Meta's side that runs in parallel with the implementation work below.

## 1. Create the Meta App

1. Go to [developers.facebook.com/apps](https://developers.facebook.com/apps) → **Create App**.
2. Choose app type **Business**.
3. Once created, from the App Dashboard add these products (each is a separate "Add Product" card):
   - **Facebook Login for Business** (powers the OAuth flow for both Instagram and Facebook Pages)
   - **Instagram Graph API**
   - **Webhooks**
   - **WhatsApp** (only if you're doing the WhatsApp section — this also provisions a free test phone number automatically)
4. Under **App Settings → Basic**, note down:
   - **App ID** → this is `META_APP_ID`
   - **App Secret** → this is `META_APP_SECRET`
5. Under **App Settings → Basic**, add your production domain to **App Domains**, and add your redirect URI under the Facebook Login product's **Valid OAuth Redirect URIs**.

These two values (`META_APP_ID`, `META_APP_SECRET`) are already referenced throughout the codebase's connector stub comments (`src/lib/connectors/*/graph-connector.ts`) and are already declared in `.env.example` — nothing to rename.

## 3. Shared plumbing: OAuth + token storage

This part is identical for Instagram and Facebook (both go through Facebook Login for Business) and structurally similar for WhatsApp (Embedded Signup instead of classic OAuth redirect). Build this once.

### 3.1 Token encryption

The schema already documents this requirement — `prisma/schema.prisma:310-311` has `PlatformConnection.accessToken`/`refreshToken` commented as **"encrypted at rest via lib/security/encryption.ts"** — but that file doesn't exist yet. Create it before storing any real token:

```ts
// src/lib/security/encryption.ts
import { createCipheriv, createDecipheriv, randomBytes } from "crypto";

const ALGORITHM = "aes-256-gcm";

function getKey(): Buffer {
  const key = process.env.TOKEN_ENCRYPTION_KEY;
  if (!key) throw new Error("TOKEN_ENCRYPTION_KEY is not set");
  return Buffer.from(key, "base64");
}

export function encryptToken(plaintext: string): string {
  const iv = randomBytes(12);
  const cipher = createCipheriv(ALGORITHM, getKey(), iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, "utf8"), cipher.final()]);
  const authTag = cipher.getAuthTag();
  return Buffer.concat([iv, authTag, encrypted]).toString("base64");
}

export function decryptToken(payload: string): string {
  const raw = Buffer.from(payload, "base64");
  const iv = raw.subarray(0, 12);
  const authTag = raw.subarray(12, 28);
  const encrypted = raw.subarray(28);
  const decipher = createDecipheriv(ALGORITHM, getKey(), iv);
  decipher.setAuthTag(authTag);
  return Buffer.concat([decipher.update(encrypted), decipher.final()]).toString("utf8");
}
```

Never store `accessToken`/`refreshToken` in plaintext — always pass them through `encryptToken()` before a Prisma write and `decryptToken()` right before making a Graph API call.

### 3.2 OAuth route handlers

Two new route handlers, both under `src/app/api/auth/meta/`:

- **`start/route.ts`** — redirects the browser to Meta's OAuth dialog:
  ```
  https://www.facebook.com/v21.0/dialog/oauth
    ?client_id={META_APP_ID}
    &redirect_uri={META_REDIRECT_URI}
    &state={csrf-token-tied-to-session}
    &scope={comma-separated-scopes-for-the-platform-being-connected}
  ```
- **`callback/route.ts`** — receives `?code=...&state=...`, verifies `state` matches the session, then exchanges the code for a token:
  ```
  GET https://graph.facebook.com/v21.0/oauth/access_token
    ?client_id={META_APP_ID}
    &client_secret={META_APP_SECRET}
    &redirect_uri={META_REDIRECT_URI}
    &code={code}
  ```
  This returns a **short-lived user access token**. Immediately exchange it for a **long-lived token** (60 days):
  ```
  GET https://graph.facebook.com/v21.0/oauth/access_token
    ?grant_type=fb_exchange_token
    &client_id={META_APP_ID}
    &client_secret={META_APP_SECRET}
    &fb_exchange_token={short_lived_token}
  ```
  Then call `GET /me/accounts` with that token to list the Pages the user manages, and for each Page, `GET /{page-id}?fields=instagram_business_account` to find the linked IG Business Account. Store the resulting **Page access token** (not the user token) encrypted in `PlatformConnection.accessToken`, plus `tokenExpiresAt`, `scopes`, and `metaAppUserId`.

Page access tokens obtained this way don't expire as long as the user token they were derived from stays valid — but you still need a refresh path: re-run the long-lived exchange before `tokenExpiresAt` using a scheduled job (see Section 7).

### 3.3 Wiring into the existing "Connect via Meta" button

`src/app/(dashboard)/settings/integrations/page.tsx` already renders a disabled **"Connect via Meta"** button per platform, waiting on real credentials. Once the above routes exist:

1. Replace the disabled button with a link to `/api/auth/meta/start?platform=instagram` (or `facebook` / `whatsapp`).
2. In the callback handler, after storing the token, run `prisma.platformConnection.update({ where: { socialAccountId }, data: { mode: "LIVE" } })` — this one field flip is what makes every page in the app start reading real data instead of demo data, because `getInstagramConnector()` / `getFacebookConnector()` / `getWhatsAppConnector()` in each platform's `index.ts` already branch on `connection.mode`.
3. Remove the `connectPlatformAction` demo-seeding call for that platform (it currently calls `seedFacebook`/`seedWhatsApp` — see `src/server/actions/settings.ts`) once you don't want new "Connect" clicks to fall back to demo seeding.

## 4. Instagram

### Required scopes

`instagram_basic`, `instagram_manage_comments`, `instagram_manage_messages`, `pages_show_list`, `pages_read_engagement`, `business_management`.

### Constraints specific to Instagram

- Only works with an **Instagram Business or Creator account** linked to a **Facebook Page**. Personal IG accounts cannot be connected via the Graph API at all — the account owner must convert to Business/Creator in the IG app first.
- The Instagram **Messaging API** (needed for AutoDM) only lets you send a DM within **24 hours of the user's last interaction** (comment or DM) — mirroring WhatsApp's window, though slightly less strict in practice for comment-triggered replies.
- Comment-to-DM automations (the core AutoDM feature) require the `instagram_manage_messages` scope specifically, which is a **restricted permission** — Meta requires a submitted screencast showing the exact comment→DM flow before granting it broadly.

### What to implement

`src/lib/connectors/instagram/graph-connector.ts` already documents the exact endpoint for every method — fill in each `notImplemented()` stub:

| Method | Endpoint |
|---|---|
| `getProfile` | `GET /{ig-user-id}?fields=username,followers_count,follows_count,media_count,biography,website` |
| `getFollowerHistory` | `GET /{ig-user-id}/insights?metric=follower_count&period=day` |
| `getPosts` | `GET /{ig-user-id}/media?fields=id,caption,media_type,media_url,thumbnail_url,permalink,timestamp` |
| `getReelInsights` | `GET /{media-id}/insights?metric=plays,reach,likes,comments,shares,saved,ig_reels_avg_watch_time` |
| `getComments` | `GET /{media-id}/comments?fields=id,username,text,timestamp` |
| `sendDirectMessage` | `POST /{ig-user-id}/messages` (Messaging API) |
| `replyToComment` | `POST /{comment-id}/replies` |
| `verifyConnection` | `GET /{ig-user-id}?fields=id` (401/190 error code means token is dead) |

Every call needs `?access_token={page_access_token}` appended (or sent as an `Authorization: Bearer` header).

### Webhooks (for real-time comment triggers)

Automations currently trigger off comments seeded directly into Postgres. For live comments to trigger an automation, subscribe to the `comments` field on the `instagram` webhook object in the Meta App Dashboard (**Webhooks → Instagram → Subscribe**), pointing at `https://yourdomain.com/api/webhooks/meta`. See Section 6 for the shared webhook handler.

## 5. Facebook (Pages + Messenger)

### Required scopes

`pages_show_list`, `pages_read_engagement`, `pages_manage_metadata`, `pages_messaging`.

### Constraints specific to Facebook

- Everything operates at the **Page** level, not the personal profile — a user connects by picking one of the Pages they administer during OAuth (`GET /me/accounts`).
- `pages_messaging` (required for the "Page Welcome Bot" style automations already seeded in `prisma/seed/facebook.ts`) has its own **24-hour standard messaging window** rule, plus narrower **Message Tags** that allow sending outside the window only for specific non-promotional purposes (e.g., `CONFIRMED_EVENT_UPDATE`) — do not use tags for promotional content, Meta actively audits this.

## 6. WhatsApp Business Platform

This is the most different of the three — it is **messaging-only** (no posts/comments/analytics-style insights beyond delivery metrics), and it is the one already modeled with real constraints in the schema (`PlatformConnection.messagingTier`, `qualityRating`, `dailyMessageLimit`) and in `src/lib/connectors/whatsapp/tiers.ts`.

### Setup steps (these happen mostly in the Meta dashboard, not in code)

1. In the App Dashboard, add the **WhatsApp** product. Meta auto-provisions a **free test phone number** you can message from immediately — good enough for development, but it can only message up to 5 phone numbers you manually verify as testers.
2. To send to arbitrary real users, you must **register your own business phone number** (a number not currently active on regular WhatsApp) under WhatsApp Manager, and complete **Meta Business Verification** for your Business Account.
3. Note down, from WhatsApp Manager:
   - **Phone Number ID** → `WHATSAPP_PHONE_NUMBER_ID`
   - **WhatsApp Business Account ID (WABA ID)** → `WHATSAPP_BUSINESS_ACCOUNT_ID`
4. Generate a **System User access token** (Business Settings → System Users) scoped to `whatsapp_business_messaging` and `whatsapp_business_management` — this is what gets encrypted into `PlatformConnection.accessToken`. Unlike the OAuth flow in Section 3, this token is generated directly in Business Manager, not via a redirect — there's no "connect" click for WhatsApp the same way as IG/FB; instead you paste this token into your own onboarding form once per business.

### The 24-hour window and messaging tiers, for real

The demo data already models this correctly (`Conversation.lastInboundAt`, `isWindowOpen()` in `src/lib/inbox.ts`) — the real API behaves exactly the same way:

- You may send **free-form (session) messages** only within 24 hours of the customer's last inbound message.
- Outside that window, you must send a pre-approved **template message** (see below).
- Every WhatsApp Business Account starts at **Tier 1** (250 unique customers messaged per rolling 24h) and scales up automatically (Tier 2 → 1,000, Tier 3 → 10,000, Tier 4 → 100,000+) based on **quality rating** (Green/Yellow/Red, driven by block rate and negative feedback) and volume over time. You cannot manually request a higher tier — Meta grants it algorithmically. `TIER_LIMITS` in `src/lib/connectors/whatsapp/tiers.ts` already encodes these exact numbers.
- **Pricing is conversation-based**, not per-message: Meta charges per 24-hour conversation window opened, at a rate that varies by country and conversation category (marketing/utility/authentication/service). Service-category conversations (customer-initiated, standard support) are currently free; marketing/utility conversations are billed. Check [Meta's current WhatsApp pricing](https://developers.facebook.com/docs/whatsapp/pricing) before launch — these rates change periodically.

### Message templates

Any message sent outside the 24-hour window **must** use a pre-approved template:

1. Create templates in WhatsApp Manager (or via `POST /{waba-id}/message_templates`), specifying category (`MARKETING`, `UTILITY`, `AUTHENTICATION`), language, and body with `{{1}}`-style variable placeholders.
2. Templates go through Meta's automated review (usually minutes, occasionally longer) before becoming `APPROVED`.
3. Send an approved template via `POST /{phone-number-id}/messages` with `type: "template"` and the template name/language/component variables.

`WhatsAppTemplateDTO` and `sendTemplateMessage()` are already defined in `src/lib/connectors/whatsapp/types.ts` — the demo connector's `getTemplates()` currently returns seeded fake templates; the real implementation just calls `GET /{waba-id}/message_templates`.

### What to implement

`src/lib/connectors/whatsapp/graph-connector.ts`:

| Method | Endpoint / approach |
|---|---|
| `getBusinessProfile` | `GET /{phone-number-id}/whatsapp_business_profile` |
| `getMessagingLimits` | `GET /{waba-id}` — read `messaging_limit_tier`, `quality_rating` fields, write them into `PlatformConnection.messagingTier`/`qualityRating`/`dailyMessageLimit` |
| `getConversations` / `getMessages` | **No listing endpoint exists.** WhatsApp only pushes messages via webhook — conversations must be built and persisted locally from the inbound webhook stream (the existing `Conversation`/`Message` Prisma models already fit this; the webhook handler in Section 6 below just needs to upsert into them instead of the demo seed doing it) |
| `sendMessage` | `POST /{phone-number-id}/messages` with `type: "text"` — only when `isWindowOpen()` is true |
| `sendTemplateMessage` | `POST /{phone-number-id}/messages` with `type: "template"` |
| `getTemplates` | `GET /{waba-id}/message_templates` |

### Webhooks (mandatory — this is WhatsApp's only way to receive messages)

Subscribe to the `messages` field under the WhatsApp product's webhook configuration. Every inbound message, delivery receipt, and read receipt arrives here. This is not optional the way it effectively is for IG/FB polling — without this webhook, an inbound WhatsApp message never reaches your app at all.

## 7. The shared webhook handler

Create `src/app/api/webhooks/meta/route.ts` to receive events for all three platforms (Meta multiplexes Instagram, Facebook, and WhatsApp through the same webhook subscription mechanism, distinguished by the `object` field in the payload: `"instagram"`, `"page"`, or `"whatsapp_business_account"`).

```ts
// GET handles Meta's webhook verification handshake (done once, when you
// register the callback URL in the App Dashboard)
export async function GET(request: Request) {
  const url = new URL(request.url);
  const mode = url.searchParams.get("hub.mode");
  const token = url.searchParams.get("hub.verify_token");
  const challenge = url.searchParams.get("hub.challenge");

  if (mode === "subscribe" && token === process.env.META_WEBHOOK_VERIFY_TOKEN) {
    return new Response(challenge, { status: 200 });
  }
  return new Response("Forbidden", { status: 403 });
}

// POST handles every real event after that
export async function POST(request: Request) {
  const signature = request.headers.get("x-hub-signature-256");
  const rawBody = await request.text();
  // 1. Verify signature: HMAC-SHA256 of rawBody using META_APP_SECRET,
  //    compare against `signature` (constant-time compare) — reject if mismatched.
  // 2. JSON.parse(rawBody), branch on payload.object.
  // 3. For each entry/change, upsert into Comment/Conversation/Message models
  //    and, for comments, run them through the existing automation-matching
  //    logic in src/lib/automations (the same matching keywords/trigger logic
  //    that already runs against seeded comments — this is the one place a
  //    real event needs to reach code that currently only runs at seed time).
  return new Response("OK", { status: 200 });
}
```

**Never skip signature verification** — an unverified webhook endpoint lets anyone POST fake "comments" or "messages" that would trigger real automations and real sends.

Register this single URL (`https://yourdomain.com/api/webhooks/meta`) against all three products' webhook subscriptions in the App Dashboard.

## 8. Token refresh (background job)

Long-lived Page tokens and WhatsApp System User tokens don't last forever. Add a scheduled job (cron, or a Vercel/Node scheduled function) that runs daily:

1. Query `PlatformConnection` where `mode = "LIVE"` and `tokenExpiresAt` is within 7 days.
2. Re-run the long-lived token exchange (Section 3.2) for IG/FB, or prompt for System User token rotation for WhatsApp (these are typically issued with very long or no expiry, but should still be rotated periodically as a security practice).
3. Update `accessToken` (re-encrypted) and `tokenExpiresAt`.
4. On failure, set `PlatformConnection.lastSyncStatus`/`lastErrorMessage` (already in the schema) so `settings/integrations` can surface a "reconnect needed" state.

## 9. App Review checklist (before real users other than you can connect)

Meta requires a screen-recorded demonstration of each permission actually being used in your app before granting it beyond your own test accounts:

- [ ] `instagram_basic`, `instagram_manage_comments`, `instagram_manage_messages`
- [ ] `pages_show_list`, `pages_read_engagement`, `pages_manage_metadata`, `pages_messaging`
- [ ] `whatsapp_business_messaging`, `whatsapp_business_management`
- [ ] `business_management`

For each: record a short screen capture showing a real user going through your OAuth connect flow and the resulting feature working (e.g., a comment triggering an automated DM), then submit under **App Review → Permissions and Features** with that recording and a written use-case description.

Also required before going live:

- [ ] **Business Verification** completed (Business Settings → Security Center)
- [ ] **Privacy Policy URL** and **Terms of Service URL** set in App Settings (required for any app requesting these permissions)
- [ ] **Data Deletion callback URL** implemented — Meta requires an endpoint users can trigger to request their data be deleted from your systems (a checkbox in App Settings points at this URL)
- [ ] App switched from **Development Mode** to **Live Mode** in the App Dashboard (only after the above)

## 10. Summary: minimum path to "one real platform working"

If you want to validate the full pipeline end-to-end before doing all three:

1. Pick **Facebook** first — it has the lightest review requirements (no Business Verification strictly required just to read your own Page's data and send Messenger replies to people who've messaged you).
2. Implement Section 3 (OAuth + encryption) and Section 5 (Facebook connector methods).
3. Implement Section 7 (webhook handler) filtering only `object === "page"` events for now.
4. Connect your own test Page, verify `getPageProfile`/`getPosts` return real data, verify a real comment triggers your existing automation-matching logic through the webhook.
5. Only then extend the same webhook handler and add the Instagram and WhatsApp connector implementations — the shared plumbing from step 2–3 doesn't need to be rebuilt per platform.
